# KDDI ISP事業者向けメールシステムへの不正アクセス（2026年6月）

## 3. 攻撃の流れ

1. 攻撃者は、KDDIがメール基盤の一部として導入していた **第三者製ソフトウェアのゼロデイ脆弱性** を悪用して侵入した。
2. システムに保存されていたメールアドレスとパスワードを窃取した。
3. 一部のパスワードが **平文（暗号化もハッシュ化もされていない状態）** で保存されていたため、攻撃者はそのパスワードでメールボックスにログインできる状態になった。

> 脆弱性があったソフトウェアの名称は公表されていない。ベンダーが公的機関への届け出と情報公開を進めているとされる。

## 4. 被害・影響

- メールアドレス 12,231,954人、パスワード 7,616,173人が漏えいした。
- 約762万人について、メールボックス内の情報（通信の中身）を第三者が閲覧できる状態になった。
- ISP各社は、利用者のパスワードを **強制的に変更** した。
- 利用者が同じパスワードを他のサービスで使い回していた場合、**リスト型攻撃** で他のサービスにも被害が広がるおそれがある（個人情報保護委員会が注意喚起）。
- KDDI自身のメールサービス（auメール、UQ mobileメール、au one netメール）は別の設備で、影響はない。

## 5. 原因

### 5.1 KDDIの説明（2026-07-06）
- 第三者製ソフトウェアの脆弱性（確認時点でゼロデイ）を悪用された。

### 5.2 総務省の指摘（2026-07-29）
- ソフトウェアの脆弱性に加えて、**複数のセキュリティ上の問題点が重なって** 発生した。
- メールシステムには本来 **多層的な防御** が敷かれるべきなのに、それが有効に機能しなかった。
- **漏えいしたパスワードが、暗号化などの安全管理措置なしで保存されていた** ことは「看過できない」。
- 最初の報告を受けてから公表まで **22日間** かかったのは、迅速な対応とは言いがたい。

### 5.3 個人情報保護委員会の指摘（2026-08-19）
- KDDIは、多くの利用者が使うシステムで、多くのパスワードを平文で保存していた。このリスクに応じて、侵入後の **横展開を防ぎ被害を最小限にする多層的な対策（アクセス制御など）** を講じるべきだったのに、十分でなかった（技術的安全管理措置の不備）。
- パスワードの平文保存は **一部のプロバイダ側の事情** によるもので、当該プロバイダにも技術的安全管理措置の不備がある。

## 6. 初動対応

- 確認当日にシステムを改修し、脆弱性に対処した。
- 4日後に、外部と通信する全サーバーにEDRを導入した。
- 第三者機関によるフォレンジック調査で、他に不審な痕跡がないことを確認した。
- ISP各社と連携して、利用者のパスワード変更（最終的には強制変更）を進めた。

## 7. 再発防止策

### 7.1 KDDIの対策（2026-07-06 公表）

**実施済み**
- システムの改修と脆弱性への対処（6/17）
- 外部通信を制御する全サーバーへのEDR導入（6/21）
- 第三者機関によるフォレンジック調査（6/23）

**今後の対策**
- 問題のソフトウェアの設計書とプログラムを、AI なども活用して分析し、潜在的な不具合や欠陥を網羅的に点検する
- ISP事業者と共に、**よりセキュリティ強度の高い通信規格への移行** を早期に進める（従来型のメールソフト利用者への影響に配慮しつつ）

### 7.2 総務省が求めた対策（2026-07-29）
- システムの **多層的な防御態勢の再検討** を含む再発防止策の徹底と加速
- 初動の技術対応、要員の確保・配置、**経営層への報告体制**、プロバイダへの **情報共有のタイミング** を検証し、全社的に体制を改善する
- 利用者への情報提供の継続と、二次被害への支援
- 業界全体のセキュリティ水準向上への貢献
- 再発防止策の実施状況と二次被害の状況を 8/31 までに報告し、その後少なくとも1年間は四半期ごとに報告する

### 7.3 個人情報保護委員会が求めた対策（2026-08-19）
- KDDI：安全管理措置の改善と、再発防止策の実施状況の報告（10/19 期限）
- 一部のプロバイダ：パスワードの平文保存に関する安全管理措置の改善
- 利用者：同じ・似たパスワードを他のサービスで使い回していないか確認し、変更する

## 8. 未公表・不明な点

- 脆弱性があったソフトウェアの名称と脆弱性の内容
- パスワードが平文で保存されていた具体的な理由（一部のプロバイダ側の事情とされる）
- 攻撃者の特定と目的

## 9. 分析: この事例から学ぶこと

- **ゼロデイは防げなくても、被害は小さくできる**：脆弱性そのものは防ぎようがなかったとしても、パスワードがハッシュ化されていれば、メールボックスの中身まで見られることはなかった。「侵入される前提」で保存データを守る（ハッシュ化、暗号化、アクセス制御による横展開の防止）のが多層防御の本質。
- **パスワードの平文保存は、どんな事情があっても避ける**：一般に、古いメール認証方式（CRAM-MD5 など）との互換のために、サーバー側で平文や復元可能な形でパスワードを持つ設計が残っていることがある。KDDIが「よりセキュリティ強度の高い通信規格への移行」を掲げたのは、こうした構造的な問題への対策と考えられる（平文保存の具体的な理由は非公表のため推測）。
- **複数の会社にまたがるシステムの責任分界**：KDDIが提供し、各ISPが設定・運用する構造で、平文保存は一部のISPの事情だった。共通基盤を提供する側も利用する側も、セキュリティ設定の責任を明確にし、危険な設定を許さない仕組みにする必要がある。
- **公表の速さも評価される**：原因を特定してから公表する方針だったが、22日間かかったことを総務省が指摘した。影響を受ける利用者が自衛できるよう、確定前でも早めに第一報を出す判断が求められる。
- **EDRは事後の導入になった**：外部と通信するサーバーへのEDR導入が事案の後だった。インターネットに面したサーバーの監視は、平時から優先すべき。
- **利用者側の教訓**：パスワードを使い回していると、一つの漏えいが他のサービスにも広がる。
