# 名古屋港統一ターミナルシステム（NUTS）ランサムウェア攻撃（2023年7月）

> 最終確認日: 2026-09-30 ／ 状態: 完了。国土交通省の検討委員会が検証し、制度的な措置まで取りまとめ済み

## 1. 概要

| 項目 | 内容 |
|---|---|
| 組織 | 名古屋港運協会（NUTS の運用者）。港湾管理者は名古屋港管理組合 |
| 対象システム | 名古屋港統一ターミナルシステム（NUTS）。名古屋港の5つのコンテナターミナルと集中管理ゲートで使われている |
| 顕在化日 | 2023年7月4日（火）午前6時30分ごろ、NUTS が停止 |
| 初期侵入 | **保守用VPN** からの侵入と見るのが適切（国交省の委員会の見解）。IPアドレス制限がなく、VPN機器と物理サーバーの脆弱性も数か月間放置されていた |
| 攻撃種別 | ランサムウェア。物理サーバー基盤と全仮想サーバーが暗号化された |
| 業務影響 | 名古屋港の全コンテナターミナルでトレーラーによる搬出入が **約2日半停止**（7/6 夕方に再開） |
| 波及 | 荷役スケジュールに影響した船舶37隻、影響したコンテナ約2万本（推計）。トヨタ自動車の4拠点の稼働停止なども報道された |
| 情報漏えい | 外部への漏えいの形跡は確認されていない（2023-07-26時点） |
| 身代金 | 脅迫文に身代金額の記載はなく、攻撃者への連絡も行っていない |
| 攻撃者 | 公式発表では明示なし。ランサムウェア「LockBit」によるものと報じられている（報道ベース） |

## 3. 攻撃の流れ

国交省の中間取りまとめ①は、感染経路の候補として次の3つを挙げた。

1. 指定ユーザーだけが使える **VPN機器** からの侵入
2. USBメモリなど外部記憶媒体からの持ち込み
3. NUTS と港運事業者とのネットワーク連携（NAT変換）経由での侵入

そのうえで、8台の物理サーバーがすべて暗号化されていることから、アプリケーション経由ではなくサーバーへの直接攻撃の可能性が高く、**VPN機器からの侵入と見るのが適切** とした。根拠は次のとおり。

- 保守用VPNは、緊急時にすぐ対応できるよう **IPアドレスの制限をかけておらず**、IDとパスワードさえ合えば、インターネット上の誰でもアクセスできる状態だった。
- VPN機器と物理サーバーについて、**数か月前から脆弱性が公表されていたのに未対応** だった。

ただし、サーバー内のデータがすべて暗号化され、ログを解析できなかったため、感染経路は断定されていない。

## 4. 被害・影響

- 名古屋港の全コンテナターミナルで、トレーラーによるコンテナの搬出入が約2日半止まった。
- 荷役スケジュールに影響が出た船舶は37隻。システムなしの手作業で荷役を続けたが、最大24時間程度遅れた。
- 搬入・搬出に影響したコンテナは約2万本（推計）。
- トヨタ自動車の愛知県・岐阜県の4拠点の稼働停止、アパレルメーカーの入荷遅延など、経済活動への影響も報じられた。

## 5. 原因（国交省 中間取りまとめ①の「問題点」）

| 領域 | 問題点 |
|---|---|
| 外部との接続 | 保守作業用の外部接続のセキュリティ対策が **見落とされていた**（一般ユーザー向けの対策に目が行き、「身内」である保守経路のリスクを見ていなかった）。**VPN機器のログを取得していなかった** |
| サーバー・ネットワーク機器 | ウイルス対策が OS 付属のセキュリティソフトだけだった。ネットワーク機器が踏み台になっていた可能性がある |
| バックアップ | 原因分析に使うログ（システムログ、アクセスログ）も暗号化され、取得できなかった。**バックアップが直近3日分だけ** で、バックアップ自体からもウイルスが見つかった。本番環境しかバックアップしておらず、開発・評価環境は対象外だった |
| 障害対応体制 | 災害用のBCPはあったが、**システム障害（サイバー攻撃）を想定したBCPがなかった**。初動でサイバーセキュリティの専門家に相談する場面がなかった（保守・開発会社はシステムの専門家であって、セキュリティの専門家ではない） |
| 運用再開時 | 感染経路を踏まえたシステムの健全性の確認・評価が十分ではなかった |

**評価された点（グッドプラクティス）**
- 発生から丸2日半という短期間で復旧した。
- システムを使わずに、手作業で船舶との荷役を続けた。
- 日ごろから研修などを通じて愛知県警と関係を築いていた。

## 6. 初動対応

- 保守会社・開発会社に復旧を依頼し、県警に通報した。
- 物流を早く再開するため、原因究明よりシステム復旧を優先した。
- バックアップから復元したが、バックアップ内にもマルウェアが残っており、駆除に時間がかかった。

## 7. 再発防止策

### 7.1 名古屋港運協会の方針（2023-07-26）

- システム保守会社・開発会社の支援を受けて、リモート接続機器やサーバーなどへの不正アクセス防止を拡大・強化する
- システム内のログ情報とバックアップをさらに充実させる
- より高度なセキュリティ対策の実現を目指す

### 7.2 国交省の委員会が示した対策（中間取りまとめ① → 最終取りまとめ）

**ターミナルオペレーションシステム（TOS）に必要な対策**
- 機器構成、ネットワーク構成、外部との接続状況の把握（資産の把握）
- サーバーやネットワーク機器の外部接続設定の見直し
- セキュリティ対策ソフトの導入とソフトウェアの定期的な更新
- システムログを含むバックアップの取得と、取得頻度・保存期間・保存場所の適切な設定
- クラウド利用時の対策、TOS と連携する外部機器への影響の考慮
- 外部委託する場合の情報セキュリティの確保

**運用に必要な体制**
- 最高情報セキュリティ責任者（CISO）と担当者の指定
- インシデント対応手順の策定と訓練
- 情報連絡体制の構築、**システム障害を想定したBCP** の策定
- 教育・研修、脆弱性や設定不備の定期検査、対策の監査
- TOS 利用契約での責任分界の明確化、保険加入の検討

### 7.3 制度的な措置（最終取りまとめ）

- **港湾運送事業法**：TOS の情報セキュリティ対策を国が審査する仕組みを導入する（事業計画に TOS の概要とセキュリティ確保に関する事項を記載させる）。
- **サイバーセキュリティ基本法**：「重要インフラのサイバーセキュリティに係る行動計画」を改定し、重要インフラ分野に **港湾分野** を位置づける方向で検討する。港湾分野向けのセキュリティガイドラインを作成する。
- **経済安全保障推進法**：TOS を使う一般港湾運送事業を、同法の対象事業とすることが必要とした。

- 感染経路の断定（ログが暗号化され、解析できなかった）
- 攻撃者の特定（公式発表では言及なし）

## 9. 分析: この事例から学ぶこと

- **保守用の入口は「盲点」になりやすい**：ユーザー向けの対策ではなく、保守ベンダー向けのVPNが入口になった。IPアドレス制限なし、多要素認証なし、パッチ未適用という「緊急時の利便性」を優先した設定が狙われた。保守経路こそ、最も厳しく管理すべき入口。
- **入口のログがないと原因がわからない**：VPN機器のログを取っておらず、内部のログは暗号化された。ログはシステムの外に転送・保管しておく。
- **バックアップの「世代」と「清浄性」**：3日分のバックアップにもマルウェアが入っていた。長めの世代を持つこと、復元した後にスキャンすること、開発・評価環境も対象に含めることが必要。
- **復旧優先の判断にはリスクがある**：社会インフラとして早期再開を優先したのは理解できるが、委員会は再開前の健全性確認が不十分だったと指摘している。「どこまで確認してから再開するか」の基準を事前に決めておくべき。
- **手作業の代替が被害を抑えた**：システムなしで荷役を続けられたことが評価された。
- **一組織の事案が制度を変えた**：港湾が重要インフラに位置づけられ、TOS のセキュリティを国が審査する仕組みにつながった。業界共通のシステムは、一か所の弱点が業界全体の問題になる。
